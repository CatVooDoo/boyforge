# Интеграция СДЭК

Проект — PHP 8 / MySQL (MariaDB), без сборки frontend. Оформление находится в `product.php` и `js/checkout.js`, оплата — в `api/yookassa/`, обработка оплаченных заказов — в `includes/order_logic.php`.

## Что реализовано

- Переключатель 5Post / СДЭК в существующем оформлении, общая Яндекс.Карта с отдельными маркерами, поиск по городу или по строке «город, улица».
- Список ПВЗ СДЭК под картой: выбор работает и при недоступной карте.
- Актуальные действующие ПВЗ России, часы работы, адрес. Общий каталог кэшируется на час в системной временной директории; перед оплатой выбранный пункт проверяется напрямую в API.
- Тариф 136 (Посылка, склад — склад), одно место. Габариты и масса задаются в `.env`. Полная стоимость доставки включает НДС и страхование объявленной стоимости товара; срок указан в рабочих днях без дня приёма груза.
- Доставку СДЭК оплачивает клиент вместе с товаром, отдельной услугой в первоначальном и закрывающем чеках ЮKassa. Доставку 5Post оплачивает продавец: для клиента доплата равна нулю. В `orders.price` остаётся цена товара, в `delivery_cost` — доставка за счёт клиента.
- После подтверждения оплаты создаётся отправление только выбранной службы. СДЭК сохраняет среду, UUID, номер, статус и ошибку; 5Post не вызывается для заказа СДЭК.
- Служба, тестовая отметка, стоимость и статус отображаются в админке; уведомления и экспорт учитывают перевозчика. Для старых Google Apps Script сохранены имена полей payload `fivepost*`.

## Подготовка существующего сайта

1. Сделать резервную копию БД и выполнить **один раз** `migrations/20261020_cdek.sql` перед выкладкой PHP. Миграция добавляет колонки к существующей таблице `orders`; старым заказам назначается `fivepost`. Код не выполняет DDL при запросах покупателей.
2. Добавить параметры СДЭК из `.env.example` в серверный `.env`. У PHP должны быть включены cURL, JSON, mbstring, PDO MySQL; временная директория доступна для записи. TLS-проверка включена. На Windows используется системное хранилище сертификатов; на Linux требуется актуальный CA bundle.
3. Для карты оставить действующий `YANDEX_MAPS_API_KEY`. СДЭК использует уже подключённые Яндекс.Карты 2.1, отдельный виджет и отдельный картографический ключ не нужны.

## Тестирование без аккаунта СДЭК

По умолчанию используется `CDEK_ENV=sandbox`. Пустые `CDEK_TEST_CLIENT_ID` / `CDEK_TEST_CLIENT_SECRET` заменяются публичной тестовой парой из [официальной документации](https://apidoc.cdek.ru/#tag/common/Podklyuchenie-k-servisu), хост — `https://api.edu.cdek.ru/v2`. Собственные тестовые ключи можно указать в этих переменных. Тестовые заказы не доставляются и не появляются в боевом личном кабинете.

Проверка API без БД, `.env`, аккаунта СДЭК и ЮKassa:

```sh
php tests/cdek.php
php tests/cdek.php --live
node tests/checkout.cjs
```

Для локальных PHP-тестов нужна PDO SQLite. `--live` использует исключительно публичный sandbox, игнорирует `.env`, отправляет вымышленные данные, получает ПВЗ Москвы, рассчитывает стоимость с объявленной ценой 3200 ₽, создаёт тестовую посылку и опрашивает её до появления номера. Каждый запуск создаёт отдельное тестовое отправление; реальных платежей и уведомлений нет. Доступ к API должен быть разрешён сетью сервера.

Для полного сценария в интерфейсе нужен существующий сайт с БД и **тестовый магазин ЮKassa**: `YOOKASSA_SHOP_ID` и `YOOKASSA_SECRET_KEY=test_...`. Выбрать товар/пол/размер → открыть оформление → СДЭК → найти город → выбрать ПВЗ → проверить стоимость/срок/итого → заполнить получателя → провести тестовую оплату. Затем открыть заказ в админке и нажать «Обновить статус» для получения трека. Можно использовать город «Москва» для совпадения с автономным smoke-тестом.

Смешивание тестовой доставки с боевой оплатой блокируется сервером до создания платежа. Обычный сценарий 5Post остаётся доступен. Смена службы очищает выбранный ПВЗ и расчёт; ответы старых запросов другой службы игнорируются.

Без `.env` и MySQL весь сайт не запускается: это существующие обязательные зависимости проекта. Автономные тесты выше позволяют отдельно проверить интеграцию без них.

## Переход на реальную доставку

После заключения договора интернет-магазина указать:

```dotenv
CDEK_ENV=production
CDEK_CLIENT_ID=<идентификатор из личного кабинета>
CDEK_CLIENT_SECRET=<секрет из личного кабинета>
CDEK_SENDER_POINT=<код фактического ПВЗ отправителя>
CDEK_FROM_CITY_CODE=<код города этого ПВЗ в СДЭК>
```

Проверить массу и размеры реальной упакованной вещи и боевые ключи ЮKassa. Пример `MSK1` / `44` предназначен для тестов и должен быть заменён данными реального отправителя. Доставка от двери, международные отправления, несколько товаров/мест и автоматическая отмена отправления здесь не реализованы. Отправитель самостоятельно привозит посылку в указанный ПВЗ.

Среда сохраняется в заказе: последующее переключение `.env` не отправит старый тестовый заказ в production. API-ключи находятся на сервере и не передаются в браузер.

## Асинхронные ответы и повторы

Ответ `ACCEPTED` означает принятие запроса, а не завершение регистрации. UUID сохраняется сразу; «Обновить статус» в админке получает номер и результат проверки (`INVALID` при отказе). Последующие статусы отправления берутся из `entity.statuses`. Поллинг выполняется по сохранённому UUID и не создаёт новую накладную.

Оплаченные заказы обрабатываются под именованной блокировкой MySQL. После сетевой ошибки при POST сохраняется `NEEDS_REVIEW`: СДЭК мог принять запрос до обрыва связи, поэтому автоматический повтор создания запрещён. При наличии UUID статус можно обновить из админки. При отсутствии UUID нужно найти отправление по номеру BOYFORGE в СДЭК и сверить результат вручную; нельзя сбрасывать статус и повторять POST без этой сверки. Ошибки доступны в заказе и `logs/order_<ID>.json`.

## Правила коммитов

Первая строка: `<task-name-or-id> | <Title in English>`. Строки body начинаются с `--ACTION описание на русском`, где ACTION — `INIT`, `COPIED`, `MOVED`, `ADDED`, `CHANGED`, `DELETED` или `REFACTORED`. Кодировка UTF-8 без BOM. Ветка этой задачи — `feature/sdek`, база — `feature/color_orders`.
